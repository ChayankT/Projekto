# 🏛 Design Decisions & Tradeoffs

| Decision | Rationale & Tradeoffs |
|---|---|
| **MongoDB Atlas** | Flexible schema that suits agile entities well, a workable free tier, and nothing to host ourselves. Tradeoff: no strict relational constraints the way an SQL database would give you. |
| **Mongoose ODM** | Gets us schema validation, `populate` for join-like queries, and a clean query API. Tradeoff: a bit of performance overhead versus the raw MongoDB driver. |
| **node-cron** | An in-process scheduler with no extra dependencies — no need for Redis or Celery at this scale. Tradeoff: its state resets on server restart, and it doesn't scale cleanly across multiple load-balanced instances. |
| **Vite + React** | Fast local dev loop with hot module replacement. Tradeoff: client-side rendered, so there's a bit more up-front load time than an SSR setup would have. |
| **Vanilla CSS** | Full control over styling, no utility-class bloat, and a dark theme that's simple to implement. Tradeoff: a custom design system and stylesheet have to be maintained by hand. |
| **No auth (MVP)** | Deliberately out of scope for now — a user switcher fills in for real login so the system stays demonstrable. Tradeoff: not production-safe as-is. |
| **Archive as soft delete, extended to stories & tasks** | Projects, stories, and tasks all follow the same pattern now: an `archived` flag (or `status: 'archived'` for projects) hides the item from normal views, and the Archive page offers a **Restore** action per item, with a separate, explicitly-confirmed **Delete Forever** step before the real (hard) delete runs. Tradeoff: an extra flag and query filter (`archived: { $ne: true }`) to thread through every listing endpoint and page that reads stories/tasks. |
| **Story/task hard deletes still cascade** | The underlying hard-delete routes are unchanged in shape: permanently deleting a project cascades all the way down to its stories, sprints, *and* those stories' tasks, and permanently deleting a story cascades to its tasks. (The project cascade previously stopped at stories/sprints and silently left tasks behind — now fixed to match what the Archive page's confirmation dialog already told people would happen.) These are only reachable now via the Archive page's "Delete Forever" action, after the item has already been archived — day-to-day board actions archive instead of hard-deleting. Tradeoff: still no undo once "Delete Forever" is confirmed. |
| **Deleting a team member is guarded, not silent** | `Project.owner` is a required field, so a user who still owns a project can't be deleted without leaving that project's owner reference dangling — the API now returns `400` in that case and asks for ownership to be reassigned first. `assignee` on stories/tasks isn't required, so those are instead cleared to `null` on delete so the item shows up as unassigned rather than quietly disappearing from workload views (My Work, Team) with a reference to a user that no longer exists. Tradeoff: deleting a prolific team member now takes an extra reassignment step instead of completing in one click. |
| **Command Palette re-fetches its index every time it opens** | Projects/stories/tasks are re-fetched each time the palette (Ctrl+K) is opened rather than once per page load, so items created earlier in the session show up in search immediately. Tradeoff: one extra round-trip of three GET requests per open — acceptable at this data scale, and only when someone actually opens the palette. |
| **Command Palette only deep-links "Create New Project"** | Project creation has one obvious global destination, so the quick action navigates to `/projects?new=project`, which opens the create dialog automatically. Story and task creation don't have an equivalent — both need a specific project (and, for tasks, a specific story) as context — so "Create New Story"/"Create New Task" quick actions were removed rather than shipped as entries that navigate to `/projects` and do nothing further. Tradeoff: creating a story or task still requires navigating into a project/story first; a context-aware version of this is tracked in `FUTURE_IMPROVEMENTS.md`. |
| **Sprint deletion returns stories to the backlog** | Removing a sprint sets `sprint: null` on its stories instead of deleting them — a sprint container going away shouldn't mean the underlying work disappears too. Tradeoff: this is inconsistent with the destructive cascades used elsewhere, which could catch someone off guard if they expect everything in a sprint to vanish together. |
| **Burndown computed on the fly, weekend-aware** | `/api/sprints/:id/burndown` recalculates the ideal/actual series from the sprint's `Task` documents and their `completedAt` timestamps on every request instead of storing daily snapshots. Burndown used to be computed from `storyPoints`; it now counts tasks instead, since task completion is a more granular, direct signal of daily progress than a point total that only updates when a whole story finishes. The ideal line spreads the sprint's total task count evenly across weekdays only, holding flat over Saturday/Sunday. Tradeoff: simpler and always in sync with the latest data, at the cost of recomputing the series each time (a non-issue at this team scale, but worth naming); velocity (`/api/sprints/velocity/:projectId`) was left on story points and wasn't part of this change. |
| **`@hello-pangea/dnd`** | A maintained fork of `react-beautiful-dnd`, used to power the drag-and-drop Kanban board. Tradeoff: another frontend dependency, and more drag-state complexity than a plain static list would need. |
| **Archiving remembers prior status; restore returns to it** | Archiving a project used to overwrite its one `status` field outright, so restoring had nowhere to go but a hardcoded `'active'`. A `statusBeforeArchive` field now stashes the status right before archiving, and every restore path reads it back instead of assuming. Any other status change clears the stash so it can't go stale. Tradeoff: one more field to keep in sync — it's cleared, not just overwritten, on every non-archive status change. |
| **"Viewing as" user persists across refetches** | `AppContext.fetchUsers` only defaults `activeUserId` to the first user in the list when nothing is already selected (checked via the functional `setActiveUserId(prev => prev || ...)` form, so it always reads the current selection rather than the value captured when the callback was first created). A stale-closure version of this previously reset the "viewing as" user back to the first person in the list on every refetch — e.g. after adding or editing someone on the Team page — even if a different user had been deliberately selected. |
| **Backlog tab count reflects the whole backlog, not the current filters** | The Backlog tab's badge count is computed straight from all of a project's stories with no sprint (`allStories.filter(s => !s.sprint).length`), independent of whatever search/priority/assignee filters are currently narrowing the board underneath it. Showing a filtered count there previously made it look like stories had disappeared whenever a filter was applied. |
| **Completion cascades down the hierarchy, not up** | Marking a project, sprint, or story as `completed` cascades that status down to everything it contains (project → sprints → stories → tasks), skipping archived items along the way. Completion itself still never cascades upward — completing every task in a story does not auto-complete the story, and finishing a story doesn't auto-complete its sprint; only a person explicitly marking the container done does that. (The reverse direction — reopening a closed container because new work appeared underneath it — *does* cascade upward; see the next row.) Tradeoff: a project/sprint/story can show 100% completion "underneath" without itself being marked complete, until someone completes it explicitly — treated as correct since only a person should decide when the container itself is done. |
| **Reopening cascades up the hierarchy — the mirror of completion cascading down** | Creating or editing a task, story, or sprint into a non-completed state walks back up the hierarchy (`backend/utils/cascadeUp.js`) and reopens anything above it that had been marked `completed`, including un-archiving a project (its `statusBeforeArchive` snapshot is cleared too, since that snapshot is for the Archive page's explicit Restore action and no longer applies once the project's been reopened this way instead). A new task reopens its story, sprint, and project; a new/edited story reopens its sprint and project; a new/edited sprint reopens its project. Rationale: a completed or archived container whose contents quietly changed underneath it would otherwise keep showing a "done" status that no longer reflects reality. Tradeoff: a few extra targeted `updateOne` calls on every create/edit that leaves something non-completed; and it's worth remembering the two cascades are asymmetric — closing propagates down automatically, reopening propagates up automatically, but nothing ever auto-completes a parent from its children. |
| **Keyboard shortcuts: page-scoped, `event.key`-based, not global** | `N` (new task) and `Shift+N` (new story) only fire on the page that already has the right context (Story Detail and a project board, respectively) — mirrors why the command palette only deep-links "Create New Project" and not story/task creation. The `useHotkey` hook matches `event.key` case-sensitively (`'n'` vs the browser's own `'N'`/`'?'` for Shift-modified keys) instead of separately tracking a `shiftKey` flag, and skips firing while the target is a text input/textarea/select/contenteditable or while a dialog is already open. A `?` shortcut opens a shortcuts-help dialog, available anywhere. Tradeoff: no single global "create" shortcut — matches the create action to whichever page can actually resolve it. |
| **"Go to" navigation is a two-key sequence (`G` then a letter), not a chord** | `useGoToHotkeys` (mounted once, app-wide, via a `GlobalHotkeys` component) arms an 800ms window on `G` and resolves the next keystroke against a route map (`D` → Dashboard, `M` → My Work, `P` → Projects, `C` → Calendar, `T` → Team, `N` → Notifications, `A` → Archive); anything else, or the window lapsing, cancels it with no effect. A sequence was chosen over more chord shortcuts (e.g. `Ctrl+1`..`Ctrl+7`) so there's room to grow the letter map without ever colliding with a browser/OS-reserved combo. It reuses `document.body.style.overflow === 'hidden'` — already set by `Dialog` and `CommandPalette` while open — as a cheap "is something modal open" check rather than introducing a dedicated global modal-state context. Tradeoff: a stray `G` followed by an unrelated keystroke within 800ms is silently swallowed (the sequence still cancels correctly, just with a brief window where an unrelated single-key shortcut, like `N`/`?`, wouldn't fire mid-sequence). |
| **`/` focuses the board search instead of a command-palette-style search** | On a project board, `/` (page-scoped, same enable/disable rules as `N`/`Shift+N`) switches to the Backlog tab if needed and focuses the existing search input, rather than opening a separate search UI. Reuses the input that's already there instead of adding a second search surface alongside the command palette. |
| **Sprint Detail's "Add Story" isn't limited to the backlog** | The picker on a sprint's own page offers every uncompleted story in the project that isn't already in *this* sprint — including stories currently sitting in a different sprint, not just backlog ones — since re-scoping a story from one sprint to another is a normal planning move and there's no reason to force a detour through the backlog first. The only hard rule is that completed stories are excluded (finished work isn't sprint-planning material) and the action itself is hidden once the sprint is `completed` (matching the same "can't target a completed sprint" rule the story edit dialog already enforces on the project board). |
| **Sprint Detail also supports creating a new story in-column, alongside pulling an existing one in** | The per-column "+"/click-to-add affordance (mirrored from the project backlog board and a story's task board) creates a brand-new story pinned to this sprint and whichever column was clicked, which is a distinct action from "Add Story" (which only re-scopes stories that already exist). Both are offered side by side rather than merged into one flow, since "make something new" and "pull something in from elsewhere" are different intents even though they land in the same place. Like "Add Story", both new affordances are hidden once the sprint is `completed`. |
| **Sprint capacity is an advisory warning, not an enforced limit** | `Sprint.capacity` (story points) is optional and compared client-side against the sum of the sprint's stories' `storyPoints`. Exceeding it surfaces a warning (an "Over capacity" badge on the project's sprint cards, and a red stat plus badge on Sprint Detail) but the backend accepts an over-committed sprint without complaint — planning is judgment-based, and a hard block would get in the way of deliberately over-committing for a known-light sprint. Tradeoff: it's possible to ignore the warning entirely; there's no server-side guardrail. |
| **Comments are a single polymorphic model, not one collection per entity type** | `Comment` uses `entityType: 'story'\|'task'` + `entityId` instead of separate `StoryComment`/`TaskComment` models, since the two need identical behavior (add, list, delete) and Mongo has no foreign-key constraint to enforce anyway. Tradeoff: `entityId` isn't a typed `ref`, so Mongoose can't `populate()` the parent story/task directly from a comment — not needed today since both mount points already have the parent's id from routing/props, but would matter if comments ever needed to be queried standalone (e.g. "all comments by user X across everything"). |
| **Comments have no edit, no threading, no author-gated delete** | Kept deliberately minimal: a chronological, flat list anyone can add to. Anyone can delete any comment, not just their own — there's no auth in this MVP (see "No auth" above) to check authorship against, so a gated delete would be theater, not real protection. Tradeoff: no correction-in-place for a typo (delete-and-repost is the only fix) and no way to have a focused sub-conversation; both are listed in `FUTURE_IMPROVEMENTS.md` if this needs to grow up. |
| **Assignment and sprint start/complete notifications reuse the existing generic `Notification` model** | `Notification` was already `{ user, message, taskId (nullable) }` — generic enough that new triggers didn't need a schema change, just new `Notification.create()` call sites in the relevant route handlers (story/task PUT+POST, sprint PUT) alongside the existing overdue-task cron job. Sprint notifications set `taskId: null` since a sprint isn't a `Task`; the message string carries all the sprint-specific context instead. Tradeoff: `Notification` doesn't record *who* triggered it (there's no acting-user concept without auth) or a structured `type`/entity reference beyond the optional task link, so building richer notification-center UI (grouping, per-type icons, "jump to the story") later would need a small schema addition then. |
| **Assignment notifications fire on any change, including self-assignment, and diff against the previous value first** | Each `PUT`/`POST` handler that accepts an `assignee` reads the record's *previous* assignee before writing, and only creates a notification when the new value differs from it — so drag-and-drop status moves, archive/restore, and edits that happen to resend the same assignee all correctly stay silent. There's no reliable "who's making this request" without auth, so assigning a task to yourself still sends yourself a notification rather than trying to suppress it — a minor, harmless redundancy rather than a real problem. |
| **Sprint start/complete notifies participants, not the whole team** | "Participants" means anyone currently assigned to one of the sprint's (non-archived) stories or tasks — computed fresh from `UserStory`/`Task` at the moment the sprint transitions, not a stored membership list (the app has no per-project team roster, only a global `Team` page). Tradeoff: someone who was assigned and then unassigned before the sprint starts/completes won't be notified, and this is a `PUT`-time snapshot, not a live subscription — matches the rest of the app's "recompute from current data on each request" philosophy (see the burndown row above) rather than introducing a new pattern. |
